## Слайд 2: Что такое SSL-сертификат и УЦ?
**Тезисы:**
*   **Цифровой сертификат:** Удостоверяет подлинность объекта и обеспечивает шифрование соединения.
*   **Удостоверяющий Центр (УЦ):** Доверенная организация, имеющая право выпускать сертификаты.
*   **Иерархия УЦ:**
    *   **Корневой УЦ (Root CA):** Первый УЦ, самоподписанный сертификат (на 5-10 лет). Хранится выключенным, включается только для выпуска выдающего УЦ. Не имеет расширений SAN, OCSP, CDP, AIA.
    *   **Выдающий УЦ (Sub/Issuing CA):** Выпускает сертификаты для конечных объектов. Не имеет SAN (чтобы не привязываться к IP). Cодержит расширения CDP и AIA, (OCSP).

---

## Слайд 3: Subject: Описание объекта
**Тезисы:**
*   **Subject** — криптографически защищенное описание объекта (материал, связанный с объектом).
*   **Для веб-сайтов:** Имя домена в `CN`, имя организации в `O`.
*   **Для MS Active Directory / Smartcards:** Полный путь LDAP, имя пользователя в `CN` или `UPN`.
*   **Для почты и подписи скриптов:** Имя пользователя в `CN`, адрес в `E`.

---

## Слайд 4: SAN (Subject Alternative Name)
**Тезисы:**
*   Позволяет защитить несколько имен, IP или объектов одним сертификатом.
*   **Типы данных в SAN:**
    *   `DNS` (DNSName) — для серверов.
    *   `IP` (IPAddress) — для серверов.
    *   `Email` (rfc822Name) — для пользователей.
    *   `UPN` / `KRB5 PrincipalName` — для смарт-карт и контроллеров домена.
*   **Пример (Сбербанк):** Один сертификат защищает `sberbank.ru`, `www.sberbank.ru`, `sbrf.ru`, `www.sbrf.ru`.

## Слайд 5: Политики валидации для публичных сайтов
**Тезисы:**
*   **DV (Domain-Validated) | OID: 2.23.140.1.2.1**
    *   Проверка только контроля над доменом.
    *   Быстрый выпуск, полная автоматизация.
*   **OV (Organization-Validated) | OID: 2.23.140.1.2.2**
    *   Проверка домена + юридического лица (требуются учредительные документы).
    *   Подтверждает официальный статус портала.
*   **EV (Extended-Validation) | OID: 2.23.140.1.1**
    *   Расширенная проверка бизнес-уровня.
    *   В настоящее время используется редко.

## Слайд 6: Проверка валидности сертификата
**Тезисы:**
*   **Через браузер:** Клик на значок замка → проверка `Subject (CN)`, сроков действия и OID политики.
*   **Через терминал (Linux):** Использование `openssl s_client` и `curl`.
*   **Импортозамещение:**
    *   Российские сайты (например, Сбербанк) теперь используют сертификаты УЦ Минцифры.
    *   Стандартные публичные OID (DV/OV) могут отсутствовать, доверие строится на национальном списке доверенных корневых сертификатов.

> **Заметки для спикера:**
> *Команда для проверки через curl:* `curl --insecure -vvI https://www.croc.ru 2>&1 | awk 'BEGIN { cert =0 } /^\* SSL connection/ { cert=1 } /^\*/ { if (cert) print }'`
> *Команда для просмотра OID политики:* `openssl x509 -noout -text -in croc.cert | grep 2.23.140`

## Слайд 7: Списки отзыва сертификатов (CRL)
**Тезисы:**
*   **CRL (Certificate Revocation List):** Список сертификатов, отозванных УЦ до истечения срока действия.
*   **Где найти ссылки для проверки?**
    *   **CDP (CRL Distribution Point):** URL для скачивания самого CRL.
    *   **AIA (Authority Information Access):** URL для скачивания сертификатов УЦ (цепочки).
    *   *Важно:* Для публикации используется только протокол **HTTP**.
*   **Delta CRL (Freshest CRL):** Содержит только *новые* отзывы с момента выпуска основного CRL. В MS CA по умолчанию имеет имя `имяфайла+.crl`.

---

## Слайд 8: Практика: Ручная проверка через CRL
**Тезисы:**
1.  Скачать CRL и сертификаты цепочки (Сервер -> SubCA -> RootCA) по ссылкам из AIA и CDP.
2.  Конвертировать CRL из DER в PEM.
3.  Собрать единую цепочку (`chain.pem` + `crl.pem`).
4.  Выполнить проверку: `openssl verify -crl_check -CAfile crl_chain.pem sberbank.pem`
*   **Проблема CRL:** Браузеры не любят CRL из-за большого размера файлов и медленной загрузки.

> **Заметки для спикера:**
> *Пример скачивания и конвертации:*
> `wget -O crl.der http://rostelecom.ru/cdp/subca_ssl_rsa2022.crl`
> `openssl crl -inform DER -in crl.der -outform PEM -out crl.pem`

## Слайд 9: Протокол OCSP
**Тезисы:**
*   **OCSP (Online Certificate Status Protocol):** Альтернатива CRL (описан в RFC 6960).
*   **Как работает:**
    *   Запрос/Ответ по протоколу HTTP (кодировка ASN.1).
    *   Позволяет получить статус отзыва конкретного сертификата в реальном времени.
*   **Сервера OCSP** называются "ответчиками OCSP".
*   Рекомендован для использования там, где CRL работает слишком медленно.

---

## Слайд 10: Key Usage (Назначение ключа)
**Тезисы:**
*   Ограничивают или разрешают операции с публичным ключом.
*   **Основные расширения:**
    *   **Digital signature:** Аутентификация, подпись данных.
    *   **Non-repudiation:** Защита от отказа от авторства (не для подписи CRL/сертификатов).
    *   **Key encipherment:** Шифрование симметричных ключей (используется в SSL).
    *   **Certificate signing / CRL signing:** Только для сертификатов УЦ.

---

## Слайд 11: Extended Key Usage (Расширенное назначение)
**Тезисы:**
*   Уточняет назначение ключа. Может быть *критичным* (строго ограничивает) или *некритичным* (информационным).
*   **Популярные сценарии:**
    *   **TLS Web server authentication:** Требует Digital signature, key encipherment или key agreement.
    *   **TLS Web client authentication:** Аутентификация клиентов.
    *   **Email protection:** Защита электронной почты (S/MIME).
    *   **Sign executable code:** Подпись кода.
    *   **Timestamping:** Проставление временных меток.
