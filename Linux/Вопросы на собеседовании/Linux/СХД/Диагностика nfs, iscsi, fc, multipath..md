Диагностика сетевых хранилищ и протоколов доступа к ним (NFS, iSCSI, FC) и технологий мультипутинга (Multipath) требует понимания как сетевого стека, так и блочной/файловой подсистемы ОС.

Ниже представлено подробное руководство по диагностике для Linux-систем (наиболее частая среда для этих технологий), разделенное по протоколам.

---

### 1. NFS (Network File System)
**Уровень:** Файловый. **Транспорт:** TCP/UDP (обычно TCP).
**Частые проблемы:** Зависание mount, ошибки "Stale file handle", низкая скорость, ошибки прав доступа.

#### Базовые команды и проверки:
*   **Проверка доступных экспортов на сервере:**
    ```bash
    showmount -e <nfs_server_ip>
    ```
*   **Проверка работы RPC-служб (Portmapper, NFS, Mountd):**
    ```bash
    rpcinfo -p <nfs_server_ip>
    ```
    *Если порты 111 (rpcbind), 2049 (nfs) недоступны — проблема в сети или firewall.*
*   **Проверка текущих mount-ов и опций:**
    ```bash
    cat /proc/mounts | grep nfs
    mount | grep nfs
    ```
*   **Сетевая диагностика (перехват трафика):**
    ```bash
    tcpdump -i eth0 -nn -s0 -w nfs_trace.pcap port 2049
    ```
    *Анализ в Wireshark покажет, на каком RPC-вызове происходит обрыв или таймаут.*
*   **Логи ядра (ошибки mount, таймауты):**
    ```bash
    dmesg -T | grep -i nfs
    journalctl -k | grep -i nfs
    ```

#### Типичные сценарии решения:
1.  **"Stale file handle":** Файл был удален на сервере, но клиент держит его дескриптор. Решение: `umount` и `mount` заново (иногда требуется `umount -l` и перезагрузка клиента).
2.  **Зависание процессов (D-state):** Проблема с сетью или NFS-сервером. Проверьте `tcpdump`. Если сервер жив, но пакеты не идут — ищите проблему в коммутаторах.
3.  **Низкая скорость:** Убедитесь, что используется **NFSv4** (или NFSv3 по TCP). UDP часто режется сетевым оборудованием. Проверьте опции `rsize` и `wsize` (должны быть 1048576 или больше).

### 2. iSCSI (Internet Small Computer System Interface)
**Уровень:** Блочный. **Транспорт:** TCP/IP.
**Частые проблемы:** Не видны LUN, обрывы сессий, падение скорости из-за MTU.

#### Базовые команды и проверки (утилита `iscsiadm`):
*   **Статус службы инициатора:**
    ```bash
    systemctl status iscsid
    ```
*   **Поиск целей (Discovery):**
    ```bash
    iscsiadm -m discovery -t sendtargets -p <target_ip>
    ```
*   **Просмотр активных сессий:**
    ```bash
    iscsiadm -m session
    ```
*   **Просмотр параметров конкретной ноды (включая CHAP-аутентификацию):**
    ```bash
    iscsiadm -m node -T <iqn_имя_цели> -p <target_ip>
    ```
*   **Логи (ошибки аутентификации, обрывы линка):**
    ```bash
    dmesg -T | grep -iE 'iscsi|scsi'
    journalctl -u iscsid
    ```

#### Типичные сценарии решения:
1.  **Discovery/Login fails:**
    *   Проверьте сеть: `ping`, `telnet <target_ip> 3260`.
    *   Проверьте CHAP-аутентификацию (пользователь/пароль в `iscsiadm` и на СХД должны совпадать).
    *   Проверьте **Zoning/LUN Masking** на стороне СХД (доступен ли WWN/iQN инициатора к конкретному LUN).
2.  **Падение скорости / Обрывы:**
    *   **КРИТИЧНО:** Проверьте MTU. Для iSCSI настоятельно рекомендуется **Jumbo Frames (MTU 9000)** на всех узлах: от HBA/NIC клиента до коммутаторов и портов СХД.
    *   Команда проверки: `ping -M do -s 8972 <target_ip>` (если идет фрагментация — MTU не сквозной).
    *   Проверьте offload-настройки сетевой карты (`ethtool -k eth0`), иногда отключение TSO/GSO решает проблемы с конкретными СХД.

### 3. FC (Fibre Channel)
**Уровень:** Блочный. **Транспорт:** Выделенная FC-сеть (оптика, HBA, FC-коммутаторы).
**Частые проблемы:** Линк не поднимается, не видны LUN, ошибки на уровне SFP/кабелей.

#### Базовые команды и проверки (через sysfs и утилиты):
*   **Статус FC-хостов (HBA) и их WWN:**
    ```bash
    cat /sys/class/fc_host/host*/port_name  # WWN (Node/Port)
    cat /sys/class/fc_host/host*/port_state # Состояние (Linkup/Linkdown)
    cat /sys/class/fc_host/host*/speed      # Скорость (например, 16 Gbit)
    ```
*   **Проверка видимости SCSI-устройств (LUN):**
    ```bash
    lsblk
    lsscsi -g
    ```
*   **Детальная информация по HBA (требуются утилиты вендоров):**
    *   QLogic: `scli` или `qlgc`
    *   Emulex (Broadcom): `hbanyware` или `elxocmcli`
    *   Универсально (если есть `sysfsutils`): `systool -c fc_host -v`
*   **Логи ядра (ошибки линка, сбросы шины, ошибки SCSI):**
    ```bash
    dmesg -T | grep -iE 'fc|qla|lpfc|scsi'
    ```

#### Типичные сценарии решения:
1.  **Port_state = Linkdown:**
    *   Физика: проверьте SFP-модули, патч-корды, порты на коммутаторе.
    *   Логика: проверьте, включен ли порт на FC-коммутаторе (Brocade/Cisco MDS) и совпадают ли скорости/режимы (Auto, 8/16/32 Gbit).
2.  **Port_state = Linkup, но `lsblk` пуст:**
    *   Проблема не на уровне ОС, а на уровне **FC-коммутатора (Zoning)** или **СХД (LUN Masking)**. WWN-порты хоста должны быть добавлены в зону на коммутаторе и замаплены на LUN на СХД.
3.  **Ошибки "resetting host" или "aborting command":**
    *   Часто связано с плохой оптикой (затухание сигнала). Проверьте уровень принимаемого сигнала (Rx Power) через утилиты вендора HBA.

### 4. Multipath (Device Mapper Multipath)
**Уровень:** Агрегация путей (работает поверх iSCSI или FC).
**Частые проблемы:** Пути в состоянии `faulty`, неверный алгоритм переключения (ALUA), дублирование устройств, конфликты конфигурации.

#### Базовые команды и проверки:
*   **Статус службы:**
    ```bash
    systemctl status multipathd
    ```
*   **Главная команда диагностики (показывает топологию, пути и их статус):**
    ```bash
    multipath -ll
    ```
    *Что должно быть в идеале:*
    *   `size=...` (размер диска)
    *   `features='...'` (например, `1 queue_if_no_path`)
    *   `hwhandler='1 alua'` (используется ALUA для Active/Passive или Active/Active СХД)
    *   Пути должны иметь статус `active` или `ready`. Не должно быть `faulty` или `ghost`.
*   **Проверка конфигурации (как multipath видит текущие настройки):**
    ```bash
    multipath -t
    ```
*   **Просмотр событий демона (смена состояний путей):**
    ```bash
    journalctl -u multipathd -f
    dmesg -T | grep -i multipath
    ```
*   **Принудительное обновление топологии (если добавили/убрали пути):**
    ```bash
    multipath -r
    ```

#### Типичные сценарии решения:
1.  **Пути в статусе `faulty`:**
    *   Multipath только *агрегирует* пути. Если путь `faulty`, значит проблема на уровне **нижележащего транспорта** (iSCSI сессия упала, FC линк down, или СХД отклала порт). Сначала чините iSCSI/FC, потом multipath.
2.  **Дублирование устройств (видны и `sda`, и `mpatha`):**
    *   В `/etc/multipath.conf` в секции `blacklist` нужно добавить устройства, которые не должны быть мультипутными (например, локальные диски `devnode "^sd[a]"` или конкретные WWN).
    *   После изменения конфига: `multipath -r` и `systemctl restart multipathd`.
3.  **Проблемы с ALUA (Asymmetric Logical Unit Access):**
    *   Если СХД Active/Passive, а multipath шлет I/O на пассивный контроллер, будут таймауты. Убедитесь, что в `multipath.conf` для вашей модели СХД прописан правильный `prio` (например, `alua`) и `path_grouping_policy` (например, `group_by_prio`).
4.  **Очистка всех multipath-устройств (ОСТОРОЖНО!):**
    ```bash
    multipath -F
    ```
    *Использовать только если нужно полностью пересобрать таблицу с нуля. Если на дисках есть ФС, данные могут повредиться!*

### 🛠 Универсальный чек-лист при падении производительности (I/O Bottleneck)

Если хранилище "тормозит", используйте эти инструменты для поиска узкого места:

1.  **Статистика блочных устройств:**
    ```bash
    iostat -xdm 1
    ```
    *Смотрите на `%util` (если 100% — диск/путь перегружен), `await` (время отклика, если > 20-50 мс для SSD/SAN — проблема на стороне СХД или сети) и `r/s`, `w/s` (IOPS).*
2.  **Трассировка блочного ввода-вывода:**
    ```bash
    blktrace -d /dev/mapper/mpatha -o trace.blktrace
    # В другом терминале:
    blkparse -i trace.blktrace
    ```
    *Показывает, какие именно процессы и с какими задержками обращаются к диску.*
3.  **Сетевые задержки (для NFS/iSCSI):**
    *   Используйте `ping -i 0.01` для проверки микро-задержек.
    *   Проверьте наличие потерь пакетов (`mtr <target_ip>`). Потери 0.1% в SAN-сети недопустимы и вызовут ретрансмиты и падение IOPS.
