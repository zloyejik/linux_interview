Диагностика проблем в операционной системе Linux требует системного подхода. Золотым стандартом в индустрии считается **методология USE** (Brendan Gregg): для каждого ресурса проверяем **U**tilization (утилизацию), **S**aturation (насыщение/очереди) и **E**rrors (ошибки).

Ниже приведено структурированное руководство по диагностике основных подсистем Linux с актуальными командами.

---

### 1. Быстрая оценка состояния (Triage)
Первые команды, которые нужно выполнить при поступлении жалобы на "тормоза" или сбой:

*   **Общая загрузка и время работы:**
    ```bash
    uptime
    ```
    *Смотрим на `load average` за 1, 5 и 15 минут. Если значение превышает количество ядер CPU, система перегружена.*
*   **Последние критические сообщения ядра:**
    ```bash
    dmesg -T | tail -n 30
    ```
    *Ищем слова `error`, `fail`, `segfault`, `Out of memory`, `I/O error`.*
*   **Сводная информация о ресурсах (современная альтернатива top):**
    ```bash
    htop
    # или
    glances
    ```

---

### 2. Диагностика CPU (Процессор)
**Симптомы:** Высокий load average, медленный отклик системы, зависание процессов.

*   **Детальная загрузка по ядрам:**
    ```bash
    mpstat -P ALL 1
    ```
    *Обратите внимание на `%iowait` (ожидание диска, норма < 5-10%), `%sys` (системные вызовы, норма < 15-20%), `%idle` (простой).*
*   **Статистика по процессам:**
    ```bash
    pidstat 1
    # или для конкретного PID:
    pidstat -p <PID> 1
    ```
*   **Контекстные переключения и прерывания:**
    ```bash
    vmstat 1
    ```
    *Высокие значения в колонках `in` (interrupts) и `cs` (context switches) указывают на чрезмерную активность сети, диска или блокировки в приложениях.*

---

### 3. Диагностика памяти (RAM)
**Симптомы:** Срабатывание OOM Killer, активный свопинг, медленная работа приложений.

*   **Баланс памяти:**
    ```bash
    free -h
    ```
    *Смотрим на `available` (доступная память), а не только на `free`. Высокое значение `buff/cache` — это нормально, ОС использует свободную память для кэша.*
*   **Признаки свопинга (подкачки):**
    ```bash
    vmstat 1
    ```
    *Колонки `si` (swap in) и `so` (swap out) должны быть близки к 0. Если они растут, системе критически не хватает RAM.*
*   **Поиск жертв OOM Killer:**
    ```bash
    dmesg -T | grep -i "out of memory"
    journalctl -k | grep -i "killed process"
    ```
*   **Детальный анализ потребления памяти процессами:**
    ```bash
    smem -t -k -p  # Требует установки пакета smem
    # или
    ps aux --sort=-%mem | head -n 15
    ```

---

### 4. Диагностика дисковой подсистемы (I/O)
**Симптомы:** Высокий `iowait`, зависание записи/чтения, ошибки "No space left on device".

*   **Статистика блочных устройств (наиболее важная команда):**
    ```bash
    iostat -xdm 1
    ```
    *   `%util`: Насколько диск загружен (100% = узкое место).
    *   `await`: Среднее время отклика в мс (для SSD/SAN норма < 5-10 мс, для HDD < 20 мс).
    *   `r/s`, `w/s`: IOPS (операций в секунду).
*   **Какой процесс нагружает диск:**
    ```bash
    iotop -o
    ```
*   **Проверка свободного места (байты и иноды):**
    ```bash
    df -h       # Свободное место в байтах
    df -i       # Свободные иноды (если закончатся иноды, записать файл будет нельзя, даже если место есть)
    ```
*   **Поиск открытых удаленных файлов (которые не освобождают место):**
    ```bash
    lsof +L1
    ```

---

### 5. Диагностика сети (Network)
**Симптомы:** Таймауты соединений, потеря пакетов, исчерпание портов.

*   **Активные соединения и порты (современная замена netstat):**
    ```bash
    ss -tulnp       # Прослушиваемые порты
    ss -s           # Сводная статистика сокетов
    ss -tan state established | wc -l # Количество установленных соединений
    ```
*   **Проверка связности и потерь:**
    ```bash
    mtr -r -c 100 <target_ip>  # Комбинирует ping и traceroute, показывает потери на каждом хопе
    ```
*   **Ошибки на интерфейсах (дропы, коллизии):**
    ```bash
    ip -s link show
    # или
    ethtool -S eth0 | grep -iE 'drop|error|miss'
    ```
*   **Глубокий анализ трафика:**
    ```bash
    tcpdump -i eth0 -nn -s0 -w capture.pcap port 80
    # Анализ файла capture.pcap проводится в Wireshark
    ```

### 6. Логи и системные службы (Systemd & Logs)
**Симптомы:** Служба не стартует, периодические сбои, аномальное поведение после обновления.

*   **Поиск упавших служб systemd:**
    ```bash
    systemctl --failed
    ```
*   **Просмотр логов конкретной службы:**
    ```bash
    journalctl -u <service_name> -e --no-pager
    # Например: journalctl -u nginx -e
    ```
*   **Логи за определенный период времени:**
    ```bash
    journalctl --since "1 hour ago" --until "now" | grep -i error
    ```
*   **Традиционные текстовые логи (зависит от дистрибутива):**
    *   RHEL/CentOS/Alma: `/var/log/messages`, `/var/log/secure`
    *   Debian/Ubuntu: `/var/log/syslog`, `/var/log/auth.log`

### 7. Продвинутые инструменты (Advanced Troubleshooting)
Когда базовых утилит недостаточно для понимания *причины* проблемы:

1.  **`strace`**: Отслеживание системных вызовов процесса. Показывает, почему программа зависла (например, ждет блокировку или файл).
    ```bash
    strace -p <PID> -T -t
    ```
2.  **`perf`**: Профилировщик ядра Linux. Помогает найти, какая именно функция ядра или приложения потребляет CPU.
    ```bash
    perf top
    perf record -g -p <PID>
    perf report
    ```
3.  **`eBPF` / `bpftrace`**: Современный стандарт трассировки без влияния на производительность. Позволяет отвечать на сложные вопросы (например, "покажи все задержки открытия файлов дольше 10 мс").
    ```bash
    # Пример скрипта bpftrace для задержек дисковых операций
    bpftrace -e 'tracepoint:block:block_rq_issue { @start[tid] = nsecs; }
                 tracepoint:block:block_rq_complete /@start[tid]/ {
                   @us[comm] = hist((nsecs - @start[tid]) / 1000);
                   delete(@start[tid]);
                 }'
    ```

### 💡 Чек-лист для наставника / инженера (Алгоритм действий)

1. **Определите масштаб:** Проблема на одном хосте или во всем кластере?
2. **Соберите метрики:** Выполните `uptime`, `dmesg -T`, `free -h`, `iostat -xdm 1`, `ss -s`. Сохраните вывод в файл для анализа.
3. **Изолируйте подсистему:** CPU, RAM, Disk или Network? (Используйте методологию USE).
4. **Найдите виновника:** Используйте `pidstat`, `iotop`, `ss` для определения конкретного PID или соединения.
5. **Изучите причину:** Посмотрите логи приложения и `journalctl`. При необходимости используйте `strace`.
6. **Документируйте:** Зафиксируйте причину и решение в базе знаний (особенно важно, если вы выступаете в роли наставника для команды).

Если у вас есть конкретный симптом (например, "сервер внезапно перезагрузился" или "процесс ест 100% CPU"), уточните его, и я предоставлю прицельный алгоритм расследования.
