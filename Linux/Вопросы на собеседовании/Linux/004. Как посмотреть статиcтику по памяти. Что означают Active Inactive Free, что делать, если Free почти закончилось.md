# Статистика памяти в Linux

## 1. Команды для просмотра

### Основные

```bash
free -h                 # Краткая сводка (самое популярное)
cat /proc/meminfo       # Полная детализация (источник правды)
vmstat 1 5              # Динамика: 5 замеров через 1 сек
```

### Продвинутые

```bash
top -o %MEM             # Процессы, отсортированные по памяти
htop                    # Интерактивный монитор
ps aux --sort=-%mem | head -20   # Топ-20 процессов по RSS
smem -t -k              # Учёт shared-памяти (PSS)
slabtop -o              # Использование slab-кэша ядром
cat /proc/buddyinfo     # Фрагментация физической памяти
```

## 2. Что означают Active / Inactive / Free
>>>>>>> origin/main

Эти поля живут в `/proc/meminfo` и описывают **страничный кэш ядра** (page cache + anonymous pages):

| Поле | Суть | Аналогия |
|---|---|---|
| **Free** | Память, которую **вообще никто** не использует — ни процессы, ни ядро | Пустые полки на складе |
| **Active** | Страницы, к которым **недавно обращались**. Ядро не будет их освобождать в первую очередь | Товары, которые часто берут с полок |
| **Inactive** | Страницы, к которым **давно не обращались**. Первые кандидаты на вытеснение (в swap или discard) | Пыльные коробки в углу склада |

Active и Inactive дополнительно делятся на:
- **Active(anon) / Inactive(anon)** — анонимные страницы процессов (стек, куча, `malloc`)
- **Active(file) / Inactive(file)** — файловый кэш (прочитанные с диска файлы)

### Ключевой момент: как ядро перемещает страницы

```
Процесс читает файл → страница попадает в Inactive(file)
Повторное обращение → ядро переносит в Active(file)
Долго не трогали    → ядро возвращает в Inactive(file)
Нужна память        → Inactive(file) сбрасывается на диск (или просто
                       выбрасывается, если чистая)
```

### Нет. Это нормально.
>>>>>>> origin/main

Linux придерживается философии: **свободная память — потраченная впустую память**. Ядро намеренно заполняет Free файловым кэшем (Buffers/Cache), чтобы ускорить дисковые операции.

```
$ free -h
              total    used    free    shared  buff/cache   available
Mem:           16Gi   12Gi   256Mi     512Mi      3.7Gi       3.2Gi
                          ^^^^                      ^^^^^^^     ^^^^^^^^^
                     «мало!»                   но это кэш,    ВОТ ЭТО
                                               его можно      важно!
                                               отдать
```

**Смотрите на колонку `available`, а не на `free`!**

`available` (ядро ≥ 3.14) — это оценка того, сколько памяти реально можно выделить новому процессу **без начала свапа**. Она включает:
- Free
- Значительную часть Buffers/Cache (reclaimable)
- Часть SReclaimable из slab

## 4. Что делать, если и Available кончается

### Шаг 1: Диагностика — кто ест память

```bash
# Топ процессов по RSS (резидентная память)
ps aux --sort=-%mem | head -20

# Более точно — PSS (доля shared-памяти)
smem -t -k -s pss

# Утечки в ядре (slab)
slabtop -o -s c | head -20
cat /proc/meminfo | grep -i slab

# Кто занял tmpfs/shmem
df -h | grep tmpfs

# Был ли OOM-killer?
dmesg | grep -i "out of memory"
journalctl -k | grep -i oom
```

### Шаг 2: Быстрые меры (без перезагрузки)

```bash
# Сбросить файловый кэш (безопасно, но обычно не нужно!)
sync
echo 3 > /proc/sys/vm/drop_caches

# Сбросить reclaimable slab
echo 2 > /proc/sys/vm/drop_caches

# Принудительно вернуть память из swap (если RAM освободилась)
swapoff -a && swapon -a        # осторожно, может занять минуты
```

> ⚠️ `drop_caches` — **не решение**, а диагностический инструмент. Если память тут же заполняется снова — проблема в процессах, а не в кэше.

### Шаг 3: Системные меры

| Действие | Команда / Как |
|---|---|
| **Добавить swap-файл** | `fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile` |
| **Настроить swappiness** | `sysctl vm.swappiness=10` (меньше = ядро дольше держит в RAM) |
| **Ограничить процесс** | systemd: `MemoryMax=2G` в unit-файле; cgroups v2 |
| **Перезапустить утечку** | Найти процесс и `systemctl restart <service>` |
| **Добавить RAM** | Физически или в облаке — если нагрузка легитимно выросла |

### Шаг 4: Глубокая диагностика утечек

```bash
# Отслеживать рост RSS процесса во времени
watch -n 5 'ps -p <PID> -o pid,rss,vsz,comm'

# Valgrind для своего приложения
valgrind --tool=massif ./my_app

# Утечки в ядре — kmemleak (если включён)
echo scan > /sys/kernel/debug/kmemleak
cat /sys/kernel/debug/kmemleak
```

## Шпаргалка: на что смотреть в `/proc/meminfo`

```
MemTotal          → сколько всего RAM
MemFree           → абсолютно пустая (обычно мало — это ОК)
MemAvailable      → реально доступная (ГЛАВНЫЙ ПОКАЗАТЕЛЬ)
Buffers + Cached  → файловый кэш (reclaimable)
SwapTotal/SwapFree→ сколько swap занято
Slab / SReclaimable → кэш ядра (inode, dentry и т.д.)
Dirty             → грязные страницы (ждут записи на диск)
AnonPages         → анонимная память процессов
```

**Правило большого пальца:** если `MemAvailable > 10–15%` от `MemTotal` и swap не растёт — система здорова, даже если `MemFree = 50 МБ`.
