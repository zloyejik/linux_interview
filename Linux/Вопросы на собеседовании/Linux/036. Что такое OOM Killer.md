**OOM Killer** (Out Of Memory Killer) — это механизм в ядре Linux, который принудительно завершает один или несколько процессов, когда в системе критически заканчивается оперативная память (включая swap-пространство). Его главная цель — пожертвовать одним или несколькими процессами, чтобы спасти всю операционную систему от полного зависания или паники ядра (kernel panic).

### 1. Как работает OOM Killer
Когда свободная память падает ниже безопасного порога, ядро запускает алгоритм выбора "жертвы". Для каждого процесса вычисляется **OOM score** (значение от 0 до 1000). Процесс с наивысшим баллом получает сигнал `SIGKILL` (Signal 9) и немедленно завершается.

На расчет `oom_score` влияют:
* **Объем потребляемой памяти**: чем больше памяти использует процесс, тем выше его score.
* **Приоритет (nice value)**: процессы с более низким приоритетом получают более высокий score.
* **Привилегии**: процессы, запущенные от имени `root`, обычно получают штраф (снижение score), чтобы система не убила критически важные сервисы.
* **Время работы**: долго работающие процессы могут получать небольшое снижение score.

### 2. Как проверить, сработал ли OOM Killer
Если процесс неожиданно исчез без следов в своих логах, первое, что стоит сделать — проверить системные логи:
```bash
# Просмотр сообщений ядра с временными метками
dmesg -T | grep -i 'out of memory'
# или
dmesg -T | grep -i 'oom'

# Альтернативно через journalctl
journalctl -k | grep -i oom
```
Вы увидите сообщение вроде: `Out of memory: Killed process 1234 (java) total-vm:2048000kB, anon-rss:1500000kB...`

### 3. Как управлять поведением OOM Killer
Вы можете влиять на то, какие процессы ядро будет "щадить", а какие "убивать" в первую очередь, через псевдофайловую систему `/proc`.

* **Просмотр текущего OOM score процесса** (замените `<PID>` на реальный ID процесса):
  ```bash
  cat /proc/<PID>/oom_score
  ```
* **Ручная настройка "защищенности"** через `oom_score_adj`:
  ```bash
  # Значение может быть от -1000 до 1000
  echo -500 | sudo tee /proc/<PID>/oom_score_adj
  ```
  * `1000`: процесс будет убит первым при нехватке памяти.
  * `0`: значение по умолчанию.
  * `-1000`: **полностью отключает** OOM Killer для этого процесса (ядро никогда не убьет его из-за нехватки памяти).

> ⚠️ **Важно**: Установка `-1000` для критически важного процесса (например, базы данных или SSH-демона) может быть полезной, но если память закончится полностью, это может привести к краху всей системы, так как ядро не сможет освободить ресурсы.

### 4. Особенности в современных средах (Docker / Kubernetes)
* В **Docker** и **Kubernetes** OOM Killer может срабатывать на уровне cgroups (контейнера), а не всей системы. Если контейнер превышает свой `memory.limit`, он будет убит с кодом выхода `137` (128 + 9).
* В **cgroups v2** появился более гибкий механизм: вместо глобального OOM Killer можно настроить локальный OOM Killer для конкретной группы процессов, а также использовать события `memory.oom` для мониторинга.

### 5. Как предотвратить срабатывание OOM Killer
1. **Мониторинг**: Настройте алерты на использование памяти (Prometheus, Zabbix и т.д.).
2. **Лимиты**: Всегда задавайте разумные лимиты памяти для приложений (особенно для JVM, Node.js, баз данных), чтобы они начинали использовать свои внутренние механизмы сборки мусора или сброса на диск до того, как ядро вмешается.
3. **Swap**: Убедитесь, что в системе настроен адекватный swap-файл или раздел (хотя для некоторых баз данных, например Elasticsearch или PostgreSQL, его иногда рекомендуют отключать или строго лимитировать).
4. **Overcommit**: Проверьте настройки `vm.overcommit_memory` в `sysctl`. По умолчанию (значение `0`) ядро разрешает выделение памяти сверх физического объема с расчетом на то, что не все процессы запросят её одновременно. Установка в `2` запретит выделение памяти сверх лимита (swap + процент от RAM), что заставит приложения получать ошибку `ENOMEM` при выделении, а не быть убитыми постфактум.
