# 🚀 Краткий курс Ansible для собеседования

## Блок 1. Фундамент (База, которую спрашивают всегда)

**1. Что такое Ansible?**
Инструмент для автоматизации (Configuration Management, Orchestration, Deployment). Написан на Python, конфигурации описываются на YAML.

**2. Главное отличие от конкурентов (Puppet, Chef, SaltStack)**
*   **Agentless (Безагентный):** Не требует установки демона на целевые серверы. Работает по протоколу **SSH** (для Linux) или **WinRM/PowerShell** (для Windows).
*   **Push-модель:** Управляющий сервер сам «пушит» конфигурации на узлы (в отличие от Pull-модели, где узлы сами забирают конфигурации).

**3. Идемпотентность (Слово-пароль №1 на собеседовании!)**
*   **Определение:** Свойство системы, при котором повторное выполнение операции приводит к тому же результату, что и однократное.
*   **Пример:** Если вы используете модуль `apt: name=nginx state=present`, первый запуск установит Nginx. Второй запуск **ничего не сделает** и вернет `ok` (а не `changed`), потому что состояние уже достигнуто.

## Блок 2. Архитектура и Основные компоненты

**1. Inventory (Инвентарь)**
Список хостов. Может быть в формате INI или YAML.
*   Хосты можно объединять в **группы** (`[webservers]`).
*   Группы можно вкладывать друг в друга (`[europe:children]`).
*   Переменные можно задавать на уровне хоста (`host_vars`) или группы (`group_vars`).

**2. Modules (Модули)**
«Рабочие лошадки» Ansible. Выполняют конкретную задачу.
*   *Управление пакетами:* `apt`, `yum`, `dnf`.
*   *Файлы:* `copy` (копирование как есть), `template` (копирование с рендерингом Jinja2), `file` (права, создание директорий).
*   *Сервисы:* `systemd`, `service`.
*   *Сеть/Другое:* `uri` (HTTP запросы), `command`/`shell` (выполнение команд).

**3. Playbook (Плейбук)**
Сценарий автоматизации на YAML. Состоит из **Play** (игр). Каждая Play привязана к группе хостов и содержит список **Tasks** (задач).

**4. Roles (Роли)**
Способ структурировать плейбуки для переиспользования.
**Структура роли (знать наизусть):**
*   `tasks/` — основные задачи.
*   `handlers/` — обработчики (рестарт сервисов).
*   `defaults/` — переменные по умолчанию (самый низкий приоритет).
*   `vars/` — переменные с высоким приоритетом.
*   `files/` — статические файлы (для модуля `copy`).
*   `templates/` — шаблоны Jinja2 (для модуля `template`).
*   `meta/` — зависимости роли от других ролей.

## Блок 3. Продвинутые механизмы (Middle/Senior уровень)

**1. Handlers (Обработчики)**
Задачи, которые выполняются **только** если они были вызваны через директиву `notify` в обычной задаче, и **только в конце** проигрывания Play (или секции).
*   *Зачем:* Чтобы не рестартовать Nginx 10 раз при обновлении 10 конфигов, а сделать это 1 раз в конце.

**2. Приоритет переменных (Variable Precedence)**
Ansible имеет сложную иерархию. От высшего приоритета к низшему:
1.  Переменные из командной строки (`-e "var=value"` / `--extra-vars`).
2.  `include_vars`.
3.  Переменные задач (task vars) / block vars.
4.  Переменные хоста (`host_vars`).
5.  Переменные группы (`group_vars`).
6.  Переменные роли (`role/vars`).
7.  Переменные по умолчанию роли (`role/defaults`) — *самый низкий*.

**3. Jinja2 и Template**
Движок шаблонов. Позволяет использовать переменные, циклы и условия в файлах.
*Пример в шаблоне:* `listen {{ nginx_port }};`

**4. Ansible Vault**
Инструмент для шифрования секретов (пароли, ключи) прямо в репозитории.
*   Команды: `ansible-vault encrypt file.yml`, `ansible-vault decrypt`, `ansible-vault view`.
*   При запуске плейбука с зашифрованными данными используется флаг `--ask-vault-pass` или указывается файл с паролем `--vault-password-file`.

**5. Условия и Циклы**
*   **Условия:** `when: ansible_os_family == "Debian"`
*   **Циклы:** `loop: "{{ my_list }}"` (устаревший синтаксис `with_items` все еще встречается, но `loop` — стандарт).

## Блок 4. Оптимизация и Отладка (Любимые вопросы Senior-ов)

**Как ускорить выполнение Ansible? (Топ вопрос!)**
1.  **Pipelining:** Включить в `ansible.cfg` (`pipelining = True`). Уменьшает количество SSH-сессий.
2.  **Forks:** Увеличить количество параллельных процессов (`forks = 20` или больше в `ansible.cfg`, по умолчанию всего 5).
3.  **Strategy:** Использовать `strategy: free` вместо `linear` (по умолчанию). При `free` быстрые хосты не ждут медленные.
4.  **Fact caching:** Включить кэширование фактов (например, в Redis или JSON-файлы), чтобы не собирать факты о системе при каждом запуске.
5.  **Gather facts:** Отключить сбор фактов (`gather_facts: no`), если они не нужны в плейбуке.

**Как отлаживать плейбуки?**
1.  Флаги детализации: `-v`, `-vv`, `-vvv`, `-vvvv` (от простого вывода до отладки SSH-соединений).
2.  Модуль `debug`: `debug: var=ansible_facts`.
3.  Сухой прогон: `--check` (покажет, что *изменилось* бы, но не применит).
4.  Дифф: `--diff` (покажет разницу в файлах при использовании `--check`).
5.  Модуль `assert`: для проверки условий (упадет с ошибкой, если условие ложно).

## Блок 5. Шпаргалка: Частые вопросы и ответы (Q&A)

**Q: В чем разница между модулями `command` и `shell`?**
**A:** `command` не передает команду в оболочку (не работают пайпы `|`, редиректы `>`, переменные окружения `$VAR`). `shell` запускает команду через `/bin/sh`, поддерживая весь синтаксис оболочки. *Best practice:* всегда стараться использовать `command` (он безопаснее и быстрее) или специализированные модули (`apt`, `file`), а `shell` — только в крайних случаях.

**Q: В чем разница между `copy` и `template`?**
**A:** `copy` просто копирует файл. `template` сначала рендерит файл через движок Jinja2 (подставляет переменные, условия), а потом копирует на хост.

**Q: Как выполнить задачу только на одном хосте из группы?**
**A:** Использовать директиву `run_once: true`.

**Q: Как выполнить задачу на управляющем сервере (Ansible Control Node), а не на целевом?**
**A:** Использовать директиву `delegate_to: localhost` (или `connection: local`).

**Q: Что такое Ansible Galaxy?**
**A:** Публичный репозиторий ролей. Можно скачивать готовые роли командой `ansible-galaxy install username.role_name`.

**Q: Как протестировать плейбук перед запуском на прод?**
**A:**
1. `ansible-playbook --check --diff` (базовая проверка).
2. `ansible-lint` (статический анализ кода на best practices).
3. **Molecule** (фреймворк для тестирования ролей: поднимает Docker-контейнеры, накатывает роль и проверяет состояние через Testinfra/InSpec).

## 💡 Лайфхаки для собеседования

1.  **Не говорите «Я пишу bash-скрипты в Ansible».** Говорите: «Я стараюсь использовать нативные модули Ansible (`apt`, `systemd`, `user`), потому что они идемпотентны и кроссплатформенны. Shell использую только как fallback».
2.  **Упомяните CI/CD.** Скажите, что плейбуки у вас лежат в Git, проходят проверку через `ansible-lint` и тестируются через `Molecule` в пайплайне (GitLab CI / GitHub Actions).
3.  **Знание облаков.** Если знаете AWS/GCP, упомяните динамический инвентарь (Dynamic Inventory) или коллекции (например, `amazon.aws`), чтобы Ansible сам получал список серверов из облака через API.
4.  **Ansible Automation Platform (AAP).** Если компания крупная, они могут использовать платную версию от Red Hat (ранее AWX / Tower). Упомяните, что знаете про веб-интерфейс, REST API и RBAC (права доступа).
