Подготовка к собеседованию по Docker требует понимания не только базовых команд, но и архитектуры, лучших практик (best practices) и умения решать практические задачи. 

Ниже представлен подробный гайд, разбитый по уровням сложности: от базы до продвинутых тем, а также список частых вопросов и практических заданий.

---

### 🟢 Уровень 1: База (Junior / Middle)

**1. Виртуальная машина vs Контейнер**
*   **ВМ:** Эмулирует железо, имеет свой полноценный гостевой ОС (Guest OS), тяжелая, изолирована на уровне гипервизора.
*   **Контейнер:** Использует ядро хостовой ОС (через namespaces и cgroups в Linux), легковесный, стартует за секунды, изолирует процессы, а не железо.

**2. Основные сущности**
*   **Image (Образ):** Неизменяемый шаблон (read-only), содержащий код, зависимости и метаданные. Состоит из слоев (layers).
*   **Container (Контейнер):** Запущенный экземпляр образа. Имеет свой читаемо-записываемый слой поверх образа.
*   **Registry (Реестр):** Хранилище образов (Docker Hub, GitLab Registry, AWS ECR).
*   **Volume (Том):** Механизм для сохранения данных (persistence), минуя копи-он-райт (Copy-on-Write) слой контейнера.

**3. Базовые команды (должны отскакивать от зубов)**
*   `docker build -t name:tag .` — сборка образа.
*   `docker run -d -p 8080:80 -v my_vol:/data --name my_app image:tag` — запуск контейнера (фон, проброс портов, томов, имя).
*   `docker ps -a` — список всех контейнеров.
*   `docker exec -it my_app /bin/sh` — зайти внутрь работающего контейнера.
*   `docker logs -f my_app` — логи.
*   `docker system prune -a` — очистка неиспользуемых данных (образов, контейнеров, сетей).

### 🟡 Уровень 2: Dockerfile и Оптимизация (Middle)

**1. CMD vs ENTRYPOINT (Классический вопрос!)**
*   `ENTRYPOINT` — задает исполняемый файл, который *всегда* будет выполнен при старте контейнера.
*   `CMD` — задает аргументы по умолчанию для ENTRYPOINT (или команду, если ENTRYPOINT нет). Легко переопределяется из командной строки при `docker run`.
*   *Паттерн:* `ENTRYPOINT ["python"]`, `CMD ["app.py"]`. При запуске `docker run myapp script.py` выполнится `python script.py`.

**2. COPY vs ADD**
*   `COPY` — просто копирует файлы из хоста в образ. **Предпочтительный вариант.**
*   `ADD` — умеет распаковывать локальные `.tar` архивы и скачивать файлы по URL (но это считается плохой практикой, лучше использовать `RUN curl/wget`).

**3. Multi-stage builds (Многоэтапная сборка)**
*   **Зачем:** Чтобы уменьшить размер финального образа. В первом этапе мы компилируем код и ставим все зависимости (включая билд-инструменты), во втором — копируем *только* артефакт сборки в чистый базовый образ (например, `alpine` или `distroless`).
*   *Пример:* Сборка Go-приложения или фронтенда (Node -> Nginx).

**4. Кэширование слоев**
*   Docker кэширует каждый слой. Если инструкция не изменилась, берется кэш.
*   **Правило:** Часто изменяемые файлы (код приложения) нужно копировать в *конце* Dockerfile, а статичные (package.json, requirements.txt) — в начале, чтобы при изменении кода не переустанавливались зависимости.

**5. `.dockerignore`**
*   Аналог `.gitignore`. Исключает `node_modules`, `.git`, `.env` из контекста сборки. Ускоряет сборку и уменьшает размер образа.

### 🟠 Уровень 3: Сети, Тома и Docker Compose (Middle / Senior)

**1. Сети в Docker**
*   **Bridge (default):** Контейнеры могут общаться друг с другом по IP, но лучше использовать DNS по имени контейнера.
*   **Host:** Контейнер использует сетевой стек хоста (нет изоляции портов, выше производительность).
*   **None:** Контейнер без сетевого интерфейса (только loopback).
*   **Overlay:** Для Docker Swarm / Kubernetes (между разными хостами).

**2. Типы монтирования**
*   **Volumes (`-v my_vol:/path`):** Управляются Docker, хранятся в `/var/lib/docker/volumes`. Лучший выбор для БД.
*   **Bind mounts (`-v /host/path:/container/path`):** Прямая привязка к файловой системе хоста. Удобно для разработки (hot-reload).
*   **tmpfs:** Хранится только в оперативной памяти хоста. Для чувствительных данных.

**3. Docker Compose**
*   Инструмент для описания multi-container приложений (YAML).
*   **Важный нюанс `depends_on`:** Он ждет, пока контейнер *запустится*, а не пока сервис внутри него *будет готов принимать соединения* (например, PostgreSQL может стартовать 10 секунд, а приложение упадет с ошибкой подключения). Для решения используют healthchecks или wait-for-it скрипты.

### 🔴 Уровень 4: Продвинутые темы и Безопасность (Senior / DevOps)

**1. Docker и Kubernetes**
*   С 1.24 версии K8s **убрал поддержку dockershim**. Kubernetes теперь не использует Docker напрямую как runtime.
*   Вместо этого используются **containerd** или **CRI-O** (они соответствуют стандарту OCI - Open Container Initiative). Docker остался инструментом для *сборки* образов на локальной машине.

**2. Безопасность контейнеров**
*   **Не запускать от root:** Создавать отдельного пользователя в Dockerfile (`USER appuser`).
*   **Read-only root filesystem:** Запуск с флагом `--read-only`, чтобы злоумышленник не мог изменить файлы внутри контейнера.
*   **Drop capabilities:** Использование `--cap-drop=ALL` и добавление только необходимых (`--cap-add=NET_BIND_SERVICE`).
*   **Сканирование образов:** Использование Trivy, Snyk или Docker Scout на этапе CI/CD.

**3. Distroless образы**
*   Образы от Google (`gcr.io/distroless/...`), которые содержат *только* приложение и его рантайм (например, libc). В них нет shell (`/bin/sh`), пакетного менеджера и утилит.
*   **Плюс:** Невозможно зайти внутрь через `docker exec` и что-то сломать/украсть. Резко снижает поверхность для атак.

### 💻 Практические задачи (Live Coding / Whiteboard)

На собеседовании могут попросить написать код или решить проблему.

**Задача 1: Написать Dockerfile для Node.js/Python приложения**
*Ожидаемый паттерн (Best Practices):*
```dockerfile
# 1. Базовый образ
FROM node:18-alpine AS builder
WORKDIR /app
# 2. Сначала копируем зависимости для кэширования
COPY package.json package-lock.json ./
RUN npm ci --only=production
# 3. Копируем код
COPY . .

# 4. Multi-stage: финальный образ
FROM node:18-alpine
WORKDIR /app
# 5. Безопасность: не root
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app .
USER appuser
EXPOSE 3000
CMD ["node", "server.js"]
```

**Задача 2: Контейнер сразу завершается после старта (Exit Code 0 или 1). Как дебажить?**
*Ответ:* 
1. `docker logs <container_id>` — посмотреть, что он вывел перед смертью.
2. `docker inspect <container_id>` — посмотреть `State.ExitCode` и `OOMKilled` (не кончилась ли память).
3. Если Exit Code 0, значит процесс отработал и завершился (например, забыли добавить `CMD` или процесс не умеет работать в foreground, а ушел в daemon).
4. Запустить с переопределением команды, чтобы зайти внутрь: `docker run -it --entrypoint /bin/sh <image>`.

**Задача 3: Как уменьшить размер образа в 10 раз?**
*Ответ:* 
1. Использовать `alpine` или `distroless` вместо `ubuntu/debian`.
2. Применить Multi-stage build.
3. Объединять `RUN` команды через `&&` и чистить кэш пакетного менеджера в том же слое (например, `RUN apt-get update && apt-get install -y gcc && rm -rf /var/lib/apt/lists/*`).
4. Использовать `UPX` (сжатие бинарников, если это Go/C++).

### 🎯 Топ-10 вопросов для самопроверки

1. Что такое Docker namespace и cgroups? *(Namespace изолирует то, что процесс видит (PID, Network), cgroups ограничивают то, что процесс может использовать (CPU, RAM)).*
2. Что будет, если выполнить `docker commit`? *(Создаст новый образ из текущего состояния контейнера. Считается плохой практикой, лучше использовать Dockerfile).*
3. Как пробросить переменные окружения при сборке и при запуске? *(При сборке: `ARG` и `--build-arg`. При запуске: `ENV` в Dockerfile или `-e` / `--env-file` при `docker run`).*
4. Чем `docker stop` отличается от `docker kill`? *(stop шлет SIGTERM, ждет 10 сек, потом SIGKILL. kill шлет SIGKILL сразу).*
5. Как контейнер понимает, что он в Docker? *(Обычно по наличию файла `/.dockerenv` или через cgroups).*
6. Что такое Docker Context и Buildx? *(Buildx — это расширенный CLI для сборки, поддерживает multi-platform (сборка под ARM из x86) и параллельные билды).*
7. Где физически хранятся образы и контейнеры в Linux? *(Обычно в `/var/lib/docker/`).*
8. Как передать секрет (пароль, ключ) в контейнер безопасно? *(Не через ENV! Использовать Docker Secrets (в Swarm) или Kubernetes Secrets, либо монтировать как tmpfs volume).*
9. Что такое Layer caching и как его "сломать"? *(Кэш ломается, если изменилась любая инструкция выше по Dockerfile, или если использовать `--no-cache` при сборке).*
10. Зачем нужен `HEALTHCHECK` в Dockerfile? *(Позволяет Docker (или оркестратору) понимать, что приложение внутри контейнера реально работает, а не просто запущен процесс).*

### 💡 Советы на самом собеседовании

1. **Думайте вслух.** Если дают задачу, не молчите. Рассуждайте: "Сейчас я хочу уменьшить размер образа, поэтому возьму alpine...".
2. **Признавайтесь в незнании, но предлагайте решение.** "Я не помню точный флаг команды, но я бы посмотрел это в `man docker-run` или документации".
3. **Делайте упор на CI/CD и продакшн.** Если вы скажете: "Я всегда настраиваю линтер для Dockerfile (hadolint) и сканирую образы на уязвимости в пайплайне", это огромный плюс для Middle/Senior позиции.
4. **Понимайте "под капотом".** Знание того, что Docker — это просто удобная обертка над технологиями ядра Linux (namespaces, cgroups, unionfs), сильно выделит вас среди тех, кто знает только команды.

Удачи на собеседовании! Если нужно разобрать какую-то тему глубже (например, написать пример docker-compose для микросервисов или разобраться с сетями) — напиши!
