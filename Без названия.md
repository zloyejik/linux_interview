Загрузка процессора на **500%** означает, что процесс `ns-slapd` (ядро сервера каталогов **389 Directory Server** или **Red Hat Directory Server**) полностью задействует **5 процессорных ядер**. 

Это критическая ситуация, которая обычно вызвана одной из следующих проблем: неиндексированный поиск (самая частая причина), проблемы с репликацией, зацикливание плагинов (например, MemberOf) или DDoS/ошибка клиента.

Ниже приведена пошаговая инструкция, как найти причину и устранить её.

---

### Шаг 1. Поиск неиндексированных запросов (Самая частая причина)
Если клиент ищет атрибут, для которого не построена база индексов, `ns-slapd` вынужден сканировать всю базу данных (Full Table Scan), что вызывает колоссальную нагрузку на CPU.

1. Откройте лог доступа (access log). Путь обычно такой:
   ```bash
   tail -f /var/log/dirsrv/slapd-<имя_инстанса>/access
   ```
2. Поищите записи со словом `UNINDEXED`:
   ```bash
   grep -i "UNINDEXED" /var/log/dirsrv/slapd-*/access | tail -n 20
   ```
3. **Что делать, если нашли:**
   Посмотрите на атрибут, по которому идет поиск (например, `mail`, `sn`, `customAttr`). Вам нужно добавить для него индекс.
   С помощью утилиты `dsconf` (или через веб-консоль Cockpit):
   ```bash
   # Пример добавления индекса для атрибута 'mail' (тип eq - точное совпадение)
   dsconf <имя_инстанса> backend index add --index-type eq --index-type sub --reindex backend_name mail
   ```
   *Обязательно дождитесь завершения переиндексации (reindex), это может занять время.*

---

### Шаг 2. Анализ логов ошибок (Errors Log)
Если в access-логе нет неиндексированных поисков, проблема может быть глубже.
```bash
tail -n 100 /var/log/dirsrv/slapd-<имя_инстанса>/errors
```
**На что обратить внимание:**
* **Проблемы с репликацией:** Сообщения о "stuck replication", "changelog processing" или конфликтах. Если сервер пытается обработать гигантский backlog изменений, CPU улетит в космос.
* **Ошибки базы данных (BDB / LMDB):** Сообщения о повреждении индексов или нехватке кэша БД.
* **Зависание плагинов:** Если вы недавно добавили пользователя в группу, содержащую десятки тысяч участников, плагин `MemberOf` может "виснуть", пересчитывая членство.

---

### Шаг 3. Выявление "агрессивного" клиента
Возможно, какой-то конкретный клиент (или скрипт) отправляет слишком сложные запросы (например, с глубокими вложенными `OR`, фильтрами `*` или рекурсией).

1. Посмотрите, с каких IP-адресов идет больше всего подключений:
   ```bash
   netstat -tnp | grep 389 | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -nr | head
   ```
2. В `access` логе найдите IP-адреса, которые генерируют тысячи `SRCH` (поисков) в секунду:
   ```bash
   awk '{print $3}' /var/log/dirsrv/slapd-*/access | sort | uniq -c | sort -nr | head
   ```
   *(Примечание: формат вывода может отличаться в зависимости от версии 389-ds, смотрите на колонку с IP или DN).*
3. **Решение:** Если это rogue-клиент (сбойный скрипт, LDAP-инъекция, бот), заблокируйте его на уровне `iptables`/`firewalld` или остановите службу на стороне клиента.

---

### Шаг 4. Проверка состояния БД и Кэша
Если база данных огромная, а кэш (Database Cache) настроен неправильно, сервер будет постоянно обращаться к диску, а процессор будет тратить ресурсы на блокировки и обработку I/O.

1. Проверьте, не уходит ли сервер в swap:
   ```bash
   free -h
   vmstat 1 5
   ```
2. Проверьте нагрузку на диск (I/O Wait):
   ```bash
   iostat -x 1 5
   ```
   Если `iowait` высокий, сервер "задыхается" из-за диска. Возможно, требуется увеличить `nsslapd-cachememsize` (размер кэша БД) в конфигурации.

---

### Шаг 5. Экстренные меры (Если сервер "лежит" и мешает работе)
Если сервис полностью завис, не отвечает на `ldapsearch`, а бизнес-процессы встали:

1. **Перезапуск службы** (это сбросит зависшие соединения и очистит память, но не решит корневую проблему, если она в конфигурации):
   ```bash
   systemctl restart dirsrv@<имя_инстанса>
   ```
2. **Временное ограничение сложности запросов**, чтобы защитить сервер от "тяжелых" LDAP-запросов:
   Вы можете ограничить количество возвращаемых записей или время выполнения поиска через `dsconf`:
   ```bash
   # Ограничение времени выполнения поиска (в секундах)
   dsconf <имя_инстанса> config replace nsslapd-timelimit=60
   
   # Ограничение размера возвращаемой записи (lookthrough limit)
   dsconf <имя_инстанса> config replace nsslapd-lookthroughlimit=5000
   ```

### Резюме (Чек-лист):
1. `grep -i unindexed /var/log/dirsrv/slapd-*/access` -> Если есть, **добавить индексы**.
2. `tail /var/log/dirsrv/slapd-*/errors` -> Если есть ошибки репликации/БД, **чинить БД/репликацию**.
3. `netstat` / `access log` -> Если один IP шлет миллион запросов, **блокировать клиента**.
4. Если ничего не помогает и сервер "умер" -> `systemctl restart dirsrv@<instance>`.

*Если вы пришлете вывод команды `grep -i "UNINDEXED" /var/log/dirsrv/slapd-*/access | tail -n 5` или последние строки из `errors` лога, я смогу подсказать точную команду для исправления!*
